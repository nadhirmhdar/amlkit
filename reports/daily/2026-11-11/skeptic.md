## What the team missed
1. **The same validators exist and are not used.** RP1 is not a missing capability; `datamodel.py` already holds `validate_birth_date`, `validate_country_code`, `validate_name_length` and friends, and the report path simply does not call them. This is the oldest pattern in the project (10-04: name lengths, sector, empty names; 11-10: last-MLRO check on mobile): a rule exists, one entry point enforces it, another does not. A single "validate" function per record type called at save time would close RP1, and a test that every field of `save_report` is either validated or listed as free text would keep it closed.
2. **Rewriting a value is worse than refusing it.** The gender mapping is one line, and nobody would have found it by testing which values are accepted; mlro-user found it only by parsing the exported XML. The class (a mapper with a default branch that guesses) should be searched for in the exporter: other mappers may fall back the same way for transaction types, ID types or country codes. I did not read them.
3. **A locked report is the real multiplier.** Both RP1 and the gender rewrite are tolerable if a wrong report can be corrected. It cannot, per mlro-user, so the only remedy is a new report and the first one stays in the audit history. Correct-and-refile (with before/after audit) is the same capability gap as CR1 (customer details cannot be corrected) and again should be designed once.
4. **Five of the last six findings concern validation at the edge** (sign-up name in mail, report fields, mobile deactivation, reason codes, unpaid scans). Almost nothing new appears in business logic. If the remaining budget is small, a one-day sweep of every input boundary against the domain validators would likely find the rest.
