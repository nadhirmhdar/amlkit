## What the team missed
1. **Two consecutive days of screening fixes, one of them a High, point at the same structural problem: the scorer is a stack of hand-tuned penalties on top of a name score.** CS-27 (country penalty on a representation mismatch), DB1 (date penalties out of order), F2b (country mismatch silences an exact name), N3c (letter variants) and QA's observation that a gender mismatch also silences an exact name are all the same shape: an additive adjustment can push an exact canonical name match below the threshold. A single floor for exact canonical name matches on the UN and UAE lists ("an adjustment may add evidence but never remove an alert unless an identifier proves a different person") would close the whole class, instead of each penalty being corrected as it is found.
2. **Nobody has run a regression corpus.** Two fixes in two days each reproduced a miss with a handful of inputs. A table of "must alert" pairs (exact name with each class of DOB error, country notation, gender field, Arabic letter variants) run on every change to the scorer would have caught CS-27 and DB1 before release. The suite has 3,010 tests and none of them states the policy.
3. **The look-back for CS-27 is still open, and DB1 widens it.** Compliance carries CS-27 as open pending deployment and a post-deploy re-screen. A re-screen after #464 alone would still miss every exact-name match with a month-typo birth date, so the look-back must wait for a DOB fix too, or be repeated.
4. **DB2 matters more than the Low it was given.** Both High findings of this week were invisible because the product stores only counts for a screening. Storing sub-threshold candidates (with the adjustments applied) is a small change and would give the MLRO a way to audit the scorer.
