# Continuous improvement log

Running daily log of production health checks and improvement suggestions
for amlkit, generated by a scheduled Claude Code routine. Pure append —
each entry is dated; prior entries are never edited or reorganized.

### 2026-08-20

- Health check: **UNKNOWN (not DOWN)** — this environment's egress proxy returned `403 Forbidden` on the CONNECT to `amlkit-720622408077.me-central1.run.app:443` for both `/` and `/about`, and identically for a `www.google.com` control request, confirming it's an organizational network policy blocking outbound HTTPS from this session, not a signal about the site itself. No real health data was obtainable today. If this recurs daily, the check needs an allowlisted egress path or a different verification method (e.g. Cloud Run's own uptime metrics) — flagging in case this needs fixing at the environment level rather than being silently "unknown" every day.
- `scripts/backup_to_gcs.ps1`, the only backup path outside litestream's own replication, is dead as a DR mechanism: it's hardcoded to one developer's local Windows path (`c:\Users\nadhi\Cluade connect\AML\*`), is manual-only (no schedule/cron wires it up), and zips the workspace rather than the live database — it would not have helped with the Aug 19 outage and isn't a real second line of defense today.
- The legacy fallback snapshot `gs://<bucket>/amlkit.db` that `entrypoint.sh` falls back to when litestream restore fails is a frozen, pre-litestream artifact — nothing writes to that path anymore (confirmed via grep), so it was already 3 days stale during the Aug 19 outage and gets staler by the day; the next litestream failure recovers to an even older state with no way to notice until it happens.
- `litestream.yml` sets no explicit `retention`/`snapshot-interval`, and nothing periodically verifies the replica actually restores cleanly — the Aug 19 corrupted segment ("decode page 7575: EOF") was only discovered because it took prod down, not proactively. A scheduled `litestream restore` to a scratch path (cron or CI) that fails loudly on corruption would catch this before it's an outage.
- `entrypoint.sh` has caused two production incidents (litestream config syntax, then the Aug 19 crash-loop) but has zero automated coverage — `.github/workflows/source-canary.yml` only runs the Python test suite and upstream-source checks, nothing lints or exercises the shell recovery logic (restore-fails → fallback → legacy snapshot) that keeps being the actual point of failure.
